# dsh-plugin-bft

Раздел «Управление требованиями» для DeepSeek Harness: очередь БФТ из Backlog.md,
документы требований и доска стадий.

Спецификация — `docs/superpowers/specs/2026-09-02-bft-requirements-ui-design.md`
в корне рабочего пространства.

## Что сейчас готово

Ядро данных: разбор вывода `backlog` CLI в типизированную модель, классификация ссылок,
чтение метки синхронизации, группировка очереди и колонок доски, поиск. Все функции
чистые — на вход строка, на выход структура. Ввода-вывода нет: ни файлов, ни процессов,
ни сети. Спавн CLI и отдача данных в браузер — следующий слой.

## Настройка

```sh
cp .env.example .env    # заполнить под свою машину
pnpm install
pnpm test               # 56 тестов
pnpm build              # сборка в lib/
```

Единственная обязательная переменная — `BFT_WORKSPACE_ROOT`, корень воркспейса, где лежат
`backlog/` и `.bft/`. Остальное имеет рабочие умолчания; полный список с пояснениями —
в `.env.example`.

## Как устроена конфигурация

`loadConfig(env)` — чистая функция: окружение приходит параметром, а не читается из
`process.env` внутри. Ядро остаётся без ввода-вывода, а тесты не подменяют глобальные
объекты. `process.env` подставляет host-слой в точке запуска:

```ts
import { loadConfig, describeConfig } from 'dsh-plugin-bft'

const config = loadConfig(process.env)
console.log(describeConfig(config).join('\n'))
```

Отсутствующая переменная и пустая строка равнозначны — обе означают «не задано», поэтому
`JIRA_TOKEN=` в `.env` не притворится заданным токеном.

## Доступы и секреты

**Токены живут только в окружении.** Ни в коде, ни в конфигах репозитория, ни в
`.env.example` их быть не должно — там только плейсхолдеры. Файл `.env` внесён в
`.gitignore` обоих репозиториев рабочего пространства.

**Без токенов плагин работает.** JIRA и Confluence нужны разделу прежде всего как ссылки:
эпик и страница требования открываются в браузере, где у вас уже есть сессия. Токен нужен
только чтобы подтягивать данные — статус эпика, заголовок страницы. Нет токена — раздел
показывает ссылку и не притворяется, что знает больше.

**Токен не печатается никогда.** `describeConfig` сообщает лишь факт наличия
(«токен задан» / «токен не задан»). Это правило распространяется на логи, сообщения об
ошибках и отчёты: диагностировать доступ по наличию флага можно, по значению — нет.
На это есть тест: сводка не должна содержать значение токена.

| Переменная | Обязательна | Назначение |
|---|---|---|
| `BFT_WORKSPACE_ROOT` | да | Корень воркспейса с `backlog/` и `.bft/` |
| `BFT_BACKLOG_BIN` | нет | Путь к `backlog`, если он не в PATH |
| `BFT_DOCS_PATH` | нет | Каталог документов, по умолчанию `.bft/documentation` |
| `BFT_INDEX_PATH` | нет | Каталог индекса, по умолчанию `.bft/index` |
| `BFT_TASK_TYPE` | нет | Тип задач БФТ, по умолчанию `bft` |
| `BFT_TEAM_NAME` | нет | Наша команда в колонке Team, по умолчанию `GDS/Платформа` |
| `BFT_INITIATIVES_SHEET_URL` | нет | Таблица инициатив — источник синхронизации |
| `JIRA_HOST` | нет | По умолчанию `https://jira.mts.ru` |
| `JIRA_TOKEN` | нет | Только для чтения данных эпика |
| `CONFLUENCE_HOST` | нет | По умолчанию `https://confluence.mts.ru` |
| `CONFLUENCE_TOKEN` | нет | Только для чтения данных страницы |

Имена `*_HOST` и `*_TOKEN` совпадают с уже принятыми в рабочем пространстве
(`GITLAB_HOST`, `GITLAB_TOKEN`), чтобы не заводить второй стиль именования.

### Если токен утёк

Отзовите его на стороне системы (JIRA, Confluence), выпустите новый, замените значение
в `.env`. Менять код не нужно — он значение токена нигде не сохраняет и не кэширует.

## Стадии требования

Канонический порядок хронологический, он же задаёт колонки доски:

```
To Do → FAST-DONE → REVIEW-DONE → DEEP-WORK → DEEP-REVIEW → DEEP-DONE → Cancelled
```

Панель требований — рабочая очередь, поэтому идёт в обратную сторону, ближе к финалу выше,
и скрывает `DEEP-DONE` и `Cancelled`.

У БФТ свой тип задачи и свой процесс: задачи других типов в раздел не попадают, а БФТ-задача
в стадии вне канона означает нарушение процесса — её возвращают в `To Do` и прогоняют заново.
