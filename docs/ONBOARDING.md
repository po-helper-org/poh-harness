# Онбординг

Пять шагов от чистой машины до рабочего контура. Шаги 1–3 делает установщик,
шаги 4–5 — вы сами, потому что это ваши учётные данные и ваш репозиторий.

## Шаг 1 — Проверить, что есть чем ставить

| Требуется | Проверка | Если нет |
|---|---|---|
| Node.js 22.19+ / 24+ | `node -v` | https://nodejs.org или `brew install node` |
| pnpm 11.7 | `pnpm -v` | `corepack enable && corepack prepare pnpm@11.7.0 --activate` |
| git | `git --version` | Xcode CLT / пакетный менеджер |
| Backlog.md *(желательно)* | `backlog --version` | `npm i -g backlog.md` |

Без Backlog.md контур поднимется, но раздел «Управление требованиями» покажет
пустую очередь: брать требования будет неоткуда.

## Шаг 2 — Клонировать и установить

```sh
git clone --recurse-submodules https://github.com/po-helper-org/poh-harness.git
cd poh-harness
./install.sh
```

Забыли `--recurse-submodules`? `install.sh` сам подтянет скиллы
(`git submodule update --init --recursive`) на первом же прогоне.

Установщик спрашивает **рабочий каталог** — это репозиторий, требования
которого вы ведёте (внутри лежат `backlog/` и `bft/`). Не каталог харнесса.
Пустой ввод (просто Enter) поднимает **демо-воркспейс** из этого репозитория
(`workspace/`) — несколько примеров требований на разных стадиях проработки,
чтобы раздел был содержательным сразу после установки. Свой воркспейс —
сразу флагом: `./install.sh --workspace ~/projects/my-workspace`.

Что он делает:

1. Проверяет окружение (см. шаг 1).
2. Подтягивает скиллы (`git submodule update --init --recursive`).
3. Ставит `dsh` CLI обычной npm-зависимостью на закреплённой версии
   (`@deepseek-ai/dsh`, dist-tag `alpha`) — без клонирования исходников
   харнесса, как `npx @deepseek-ai/dsh web` в апстриме.
4. Собирает `plugins/dsh-plugin-bft` (и `dsh-plugin-caveman` — только с
   `--with-caveman`).
5. Генерирует профиль
   `.dsh-data/profiles/web/{package.json,cordis.patch.yml,pnpm-workspace.yaml}`
   из шаблонов `profile/*.tpl`, подставляя пути вашей машины и корни скиллов.
6. Ставит npm-зависимости профиля (харнесс, `dsh-plugin-subscriptions`,
   `dsh-result-only-view`).

Установщик идемпотентен: гоняйте повторно после `git pull`, прежние версии
конфигов профиля он кладёт рядом как `*.bak-<timestamp>`.

## Шаг 3 — Запустить

```sh
./scripts/start-web.sh
```

В выводе будет строка вида `dsh web: http://127.0.0.1:3082/?token=…` — откройте
её. Токен новый после каждого рестарта; старая вкладка перестанет работать, это
ожидаемо.

Что должно быть видно сразу: слева внизу кнопка **«Управление требованиями»**
с демо-задачами (если использовали демо-воркспейс) или пустой очередью (если
свой воркспейс ещё без задач типа `bft`).

## Шаг 4 — Подключить подписку

Харнессу нужен LLM-провайдер. Плагин `dsh-plugin-subscriptions` позволяет
использовать подписку, которая у вас уже есть, вместо отдельного API-ключа.

1. В интерфейсе откройте **Settings** (шестерёнка внизу сайдбара).
2. Раздел подписок — выберите провайдера: ChatGPT (Codex), Claude, Grok
   (X Premium) или GitHub Copilot.
3. Войдите по OAuth в открывшемся окне. Учётные данные складываются в
   `.dsh-data/` — этот каталог в `.gitignore` и никуда не уезжает.
4. Выберите модель по умолчанию там же в настройках.

Альтернатива, если подписки нет: обычный API-ключ провайдера в тех же
настройках. Плагин подписок при этом просто не используется.

> Ключи и токены живут только на вашей машине. Ни один файл этого репозитория
> не содержит учётных данных, и `.dsh-data/` в git не попадает.

## Шаг 5 — Настроить окружение под свой воркспейс

Установили контур с демо-воркспейсом и теперь хотите перейти на свой —
`./install.sh --workspace ~/projects/my-workspace` перегенерирует профиль.

### 5.1 Требования из Backlog.md

Раздел «Управление требованиями» читает задачи типа `bft` из бэклога вашего
рабочего каталога. Минимум, чтобы очередь ожила:

```sh
cd <ваш-рабочий-каталог>
backlog init                       # если бэклога ещё нет
backlog task create "Первое требование" --type bft
```

Плагин ждёт в воркспейсе:

| Путь | Зачем |
|---|---|
| `backlog/` | Задачи. Тип задачи-требования настраивается (`BFT_TASK_TYPE`, по умолчанию `bft`). |
| `bft/documentation/<slug>/<slug>.html` | HTML-документ требования — открывается на детальной странице. |
| `bft/index/` | Индекс контекста (строится скиллом `/bft-index`), опционален. |
| `.claude/skills/` | Скиллы воркспейса, подключены как нативный skill-root — в дополнение к submodule'ам из `skills/`. |

### 5.2 Необязательные переменные окружения

Плагин работает без них — они только расширяют возможности. Образец со всеми
ключами и комментариями: `plugins/dsh-plugin-bft/.env.example`.

```sh
cp plugins/dsh-plugin-bft/.env.example plugins/dsh-plugin-bft/.env
```

Самое полезное:

- `BFT_TASK_TYPE` — если требования у вас не типа `bft`.
- `BFT_DOCS_PATH` / `BFT_INDEX_PATH` — если документы лежат не в `bft/`.
- `JIRA_HOST` / `CONFLUENCE_HOST` — включают распознавание эпик- и
  Confluence-ссылок отдельным полем; без них они остаются обычными ссылками.
- `JIRA_TOKEN` / `CONFLUENCE_TOKEN` — подтягивать статус эпика и заголовок
  страницы. Без них ссылки просто остаются ссылками.

`.env` в git не попадает.

### 5.3 Скиллы

Установщик уже подключил три submodule'а po-helper-org (`skills/poh-bft-writer`,
`skills/poh-okr-agent`, `skills/poh-helper`) — семейство `/bft-*` (генерация и
проработка требований) доступно сразу. `<ваш-воркспейс>/.claude/skills` — ещё
один корень, для собственных скиллов вашей команды.

### 5.4 Режим фокуса

Плагин `plugins/dsh-focus-mode-plugin` (подмодуль `po-helper-org/poh-focus-mode-plugin`)
приезжает вместе с клоном и включается сам: кнопка **«Фокус»** появляется в подвале левой
панели. Журнал сессий ляжет в `<ваш-воркспейс>/.focus/journal.jsonl` — обычный текстовый
файл, по строке на событие; его можно читать глазами и положить в git.

Настройки режима (норма дня, длительность, дыхание, строгость ассистента) живут в самом
журнале и правятся на вкладке «Настройки» в панели — в `profile/*.tpl` их нет намеренно.

Необязательное окружение — календарь как источник задач дня:

- `FOCUS_CALENDAR_ICS_FILE` — путь к `.ics` относительно воркспейса. Подходит, когда
  календарь выгружается файлом (в том числе из корпоративного Exchange).
- `FOCUS_CALENDAR_ICS_URL` — приватная ссылка на подписку. **Это доступ к календарю
  целиком**, поэтому она читается только из окружения процесса харнесса и в
  `profile/*.tpl` не попадает.

Без них режим работает: задачи берутся из Backlog.md, из недавних сессий и из ручного
ввода. Полный список ключей — `plugins/dsh-focus-mode-plugin/.env.example`.

## Проверка, что всё сошлось

1. Кнопка «Управление требованиями» открывает панель со списком требований.
1. Кнопка «Фокус» открывает панель режима: онбординг при первом запуске, дальше — выбор задачи и длительности.
2. «Обновить» открывает чат с подставленной командой — **без автоотправки**,
   Enter жмёте вы.
3. Клик по требованию открывает превью, оттуда — детальная страница с документом.
4. Внизу панели «Открыть доску требований» показывает доску по стадиям.
5. В чате доступны инструменты `backlog_*` (задачи) и `context7` (документация),
   а скилл `skill(bft-writer)` виден модели.

Что-то из этого не сошлось — [docs/TROUBLESHOOTING.md](TROUBLESHOOTING.md).
Полный сценарий с демо-воркспейсом — [docs/HOWTODEMO.md](HOWTODEMO.md).
